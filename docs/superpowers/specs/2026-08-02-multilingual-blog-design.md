# Shawn's Blog 多语言与自动翻译设计

日期：2026-08-02  
状态：已获用户批准，等待书面规格复核

## 1. 目标

为现有 Next.js 16 App Router 博客增加完整的简体中文、英文和日文支持。简体中文是默认语言，不根据浏览器语言自动切换；访客可以手动切换语言，系统会记住选择。

多语言范围包括：

- 公开博客的导航、搜索、文章、日记、分类、标签、相册、友链、关于、评论区、错误页和辅助提示。
- 后台管理的导航、列表、编辑器、弹窗、通知和错误提示。
- 文章、日记、分类与标签等存储在 Supabase 中的动态内容。
- 页面元数据、站点地图、canonical 与 `hreflang`。

以下内容不翻译：

- 用户评论正文、用户名和邮箱。
- Markdown 代码块、行内代码、URL、图片地址和资源路径。
- 文章与日记的 slug。
- 无需本地化的品牌名和专有名称。

## 2. 已确认的产品规则

### 2.1 语言和路由

支持的语言固定为：

| 语言 | 内部代码 | 公开 URL |
| --- | --- | --- |
| 简体中文 | `zh-CN` | 无前缀，例如 `/posts/hello` |
| 英文 | `en` | `/en` 前缀，例如 `/en/posts/hello` |
| 日文 | `ja` | `/ja` 前缀，例如 `/ja/posts/hello` |

三种语言共用文章、日记、分类和标签的 slug。API 路由继续使用 `/api/...`，不添加语言前缀。

首次访问且没有语言偏好记录时显示简体中文。系统不读取 `Accept-Language`，也不根据浏览器语言切换。访客手动切换后，语言选择写入站点 Cookie；明确带 `/en` 或 `/ja` 前缀的 URL 始终优先于 Cookie。站内链接保持当前语言。访问无语言前缀的入口时，有已保存偏好的真实访客可转到对应语言路径；没有偏好的访客、搜索引擎和未携带 Cookie 的请求始终得到简体中文。

语言切换应尽量保持当前页面：

- `/posts/hello` → `/en/posts/hello` → `/ja/posts/hello`
- `/admin/posts` → `/en/admin/posts` → `/ja/admin/posts`
- 如果目标语言路由不存在，则进入该语言首页。

### 2.2 内容发布与回退

- 中文是唯一原稿和事实来源。
- 英文、日文由 DeepSeek 自动生成，不提供人工审核或人工修改流程。
- AI 翻译成功后直接公开。
- 新内容或已变更内容在译文同步完成前，英文和日文页面显示简体中文，并显示“翻译将在下次同步后提供”的本地化提示。
- 旧译文在重新翻译失败时保留在数据库中以便恢复，但哈希不匹配的过期译文不对外展示；页面回退到最新中文原稿。
- 评论正文保持发表时的原语言，只翻译评论区界面。

## 3. 技术方案选择

采用以下组合：

- `next-intl`：Next.js 路由、本地字典、服务端组件和客户端组件的界面国际化。
- Supabase 翻译表：保存动态内容译文、源内容指纹、分块信息和同步状态。
- DeepSeek 官方 API：生成英文与日文译文。
- Vercel Cron：每天定时执行差异检查与翻译。

未采用的方案：

1. 自制 React Context 国际化：需要重复实现服务端组件、路由、元数据、缓存和 SEO 逻辑，维护成本更高。
2. 在原表直接增加 `title_en`、`content_en` 等列：表结构会随语言和内容类型膨胀，不适合分块差异、错误记录和后续扩展。

`next-intl` 是随应用部署的代码库，不是外部翻译服务，不产生按调用计费。外部翻译请求仅发送到 DeepSeek。

## 4. 应用架构

### 4.1 路由层

博客与后台页面进入统一的语言路由树，由 Next.js 16 的 `proxy.ts` 和 `next-intl` 路由配置处理“默认语言无前缀”的规则。代理必须排除：

- `/api`
- `/_next`
- 静态文件和带扩展名的资源
- Supabase 认证所需的非本地化回调（如项目存在）

路由配置关闭浏览器语言检测。URL 是当前请求语言的第一事实来源，Cookie 只用于记住用户主动做出的选择。

### 4.2 固定界面字典

项目内维护三个本地字典：

```text
messages/
├── zh-CN.json
├── en.json
└── ja.json
```

字典使用稳定的语义键，例如：

```json
{
  "navigation": {
    "home": "首页",
    "archive": "归档"
  }
}
```

固定界面文案不调用 DeepSeek 运行时翻译。三份字典随代码审查和构建一起维护，构建或测试必须检查 key 完整性。后台管理也使用同一套字典体系，但可按命名空间拆分，避免单个文件难以维护。

### 4.3 语言切换器

顶部 Header 在桌面端和移动端增加语言菜单：简体中文、English、日本語。

切换操作：

1. 计算当前页面在目标语言下的 URL。
2. 写入站点语言 Cookie，建议名称为 `BLOG_LOCALE`，`path=/`、`sameSite=lax`，有效期一年；生产环境使用 `secure`。
3. 导航到目标 URL。
4. 更新 `<html lang>`，日期、月份和可访问性文本随语言变化。

## 5. 数据模型

中文原稿继续保存在现有的 `posts`、`diaries`、`categories` 和 `tags` 表中。新增下列表：

### 5.1 `post_translations`

- `post_id uuid`：外键指向 `posts(id)`，`ON DELETE CASCADE`
- `locale text`：只允许 `en`、`ja`
- `title text`
- `excerpt text`
- `content text`
- `source_hash text`
- `source_blocks jsonb`
- `translated_blocks jsonb`
- `status text`：`pending`、`processing`、`complete`、`failed`
- `retry_count integer`
- `last_error text`
- `translated_at timestamptz`
- `created_at timestamptz`
- `updated_at timestamptz`
- 唯一键：`(post_id, locale)`

### 5.2 `diary_translations`

结构与文章译文相同，但不包含 `excerpt`，外键指向 `diaries(id)` 并级联删除。

### 5.3 `category_translations` 与 `tag_translations`

分别关联中文分类和标签，保存：

- 父记录 ID
- `locale`
- 翻译后的 `name`
- `source_hash`
- 同步状态、错误和时间字段
- 父记录删除时级联删除

### 5.4 `translation_runs`

用于后台状态和故障排查：

- 运行 ID、触发来源（`cron` 或 `admin`）
- 开始、完成时间
- 扫描、复用、翻译、失败和删除数量
- 使用的模型 ID
- 总体状态和不包含密钥的错误摘要

翻译表的公开读取策略只允许读取 `complete` 且源哈希仍匹配的内容。写入仅允许服务端 Service Role。后台状态接口需要管理员身份。

## 6. 差异检测与 Token 控制

### 6.1 内容指纹

每次保存中文原稿时只标记相关译文为 `pending`，不调用 DeepSeek。每日任务重新计算规范化后的 SHA-256 哈希：

- 标题、摘要、分类名和标签名单独计算字段哈希。
- Markdown 正文先确定性分块，再为每个块计算哈希。
- 完整 `source_hash` 用于快速判断整篇内容是否完全未变。

### 6.2 Markdown 分块

正文按 Markdown 结构划分为稳定块，包括：

- 标题和普通段落
- 列表项与引用
- 表格
- 代码块和行内代码保护区
- 图片、链接和原始 HTML 保护区

每个块保存规范化源文本、哈希、出现序号和译文。比较时：

- 哈希相同：复用已有译文，即使块在文章中移动。
- 新增或修改：只把对应文本块发送给 DeepSeek。
- 删除：从重建后的译文中移除，不产生 API 调用。
- 代码块、URL、图片路径和纯结构块直接复制，不发送给模型。

同一同步周期内，多个待翻译块可以按语言批量请求，以减少重复提示词开销；批次必须受最大字符数和模型上下文限制约束。一天内对同一中文内容的多次修改只翻译凌晨 2 点时的最终版本。

### 6.3 返回校验

DeepSeek 请求为每个块提供不可变 ID，并要求返回结构化 JSON。保存前必须验证：

- 每个请求块都有且只有一个返回结果。
- 块 ID 没有改变。
- Markdown 围栏、链接目标、图片地址和受保护占位符保持一致。
- 返回文本非空且不是错误说明。
- 返回数据可以安全重建完整 Markdown。

校验失败的批次不覆盖已有译文，记录失败原因并等待下次重试。

## 7. DeepSeek 集成

服务端使用环境变量：

```env
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_TRANSLATION_MODEL=
CRON_SECRET=
```

`DEEPSEEK_TRANSLATION_MODEL` 必须填写 DeepSeek 控制台当前提供的准确 V4 Flash API 模型 ID。模型 ID 不写死在源代码中，因此模型更名或更换版本不需要数据库迁移或代码改动。

翻译请求规则：

- 只从服务器调用，API Key 永不进入 `NEXT_PUBLIC_*` 变量或浏览器包。
- 为英文和日文分别请求，单语言失败不回滚另一语言的成功结果。
- 提示词要求准确翻译、保持语气、禁止补充事实、保护 Markdown 和占位符。
- 设置合理超时、有限并发和指数退避；限流或服务错误进入下次任务重试。
- 日志不得记录 API Key、Authorization 请求头或完整敏感响应。
- 只向 DeepSeek 发送需要翻译的已发布博客内容；评论和后台认证数据不发送。

## 8. 定时同步

Vercel Cron 每天北京时间凌晨 2 点触发。Vercel 使用 UTC，因此 cron 表达式为：

```text
0 18 * * *
```

即每天 UTC 18:00，对应次日北京时间 02:00。

Cron 调用受保护的 Route Handler，例如 `/api/cron/translations`，并校验 `Authorization: Bearer <CRON_SECRET>`。处理流程：

1. 创建 `translation_runs` 记录并取得防重入锁。
2. 扫描已发布文章、全部公开日记、分类和标签。
3. 删除已不存在父记录所遗留的数据；正常情况下由外键级联完成。
4. 跳过源哈希完全一致的记录。
5. 为英文和日文重用未变化块并翻译变化块。
6. 原子保存校验通过的译文。
7. 更新运行统计并刷新 posts、diaries、categories、search 和 sitemap 等缓存。
8. 到达运行时间或批次数上限时安全结束，剩余 `pending` 记录留到下次继续。

后台提供“立即执行同步”按钮，调用管理员鉴权的服务端入口。它复用相同同步器，仅改变触发来源，不绕过锁、批次限制或安全校验。正常内容保存不会立即翻译。

## 9. 查询、展示与搜索

### 9.1 内容查询

- 简体中文页面直接读取原表。
- 英文和日文页面读取对应翻译表。
- 只有 `complete` 且 `source_hash` 与当前中文原稿匹配时使用译文。
- 其他情况返回中文原稿并显示本地化的待翻译提示。
- 页面上的分类、标签、日期和月份使用当前 locale；slug 和资源 URL 不变。

### 9.2 搜索

- 中文搜索查询原始文章和日记。
- 英文搜索优先查询英文译文。
- 日文搜索优先查询日文译文。
- 尚无有效译文时，可将匹配的中文结果作为带回退提示的结果返回。
- API 接受经过白名单验证的 locale 参数，不接受任意表名、列名或排序表达式。

### 9.3 缓存

现有公开数据缓存按 locale 隔离，避免英文请求命中中文缓存。同步成功后按内容类型清理三种语言的相关缓存。读取请求不依赖 `cookies()` 决定译文；进入语言路由后以 URL locale 为准，以免无谓地将静态页面全部变为动态渲染。

## 10. 后台翻译管理

后台在三种语言下都可使用，并增加翻译管理页面，展示：

- 上次同步开始和完成时间。
- 当前 DeepSeek 模型 ID，不显示 API Key。
- 等待、处理中、完成、失败的记录数量。
- 每篇文章和日记的英文、日文状态。
- 失败原因摘要和重试次数。
- “立即执行同步”按钮。

界面不能提供人工编辑 AI 译文的入口，因为已确认不进行人工审核。管理员仍可通过修改中文原稿让下一次任务重新生成对应变化块。

## 11. SEO 与可访问性

- 每个语言页面生成正确的 `<html lang>`。
- 每种已有路由生成本地化 title 和 description。
- 页面输出自身 canonical，并为中文、英文、日文提供 `hreflang` alternate；可增加 `x-default` 指向简体中文。
- sitemap 包含三个语言版本的公开页面，未完成译文的语言页面仍可访问中文回退，但应在译文完成前避免作为独立已翻译内容提交给搜索引擎。
- 语言切换器具备本地化 `aria-label`、当前语言状态和键盘操作能力。
- 日期使用同一时区规则，并根据 locale 格式化名称和顺序。

## 12. 错误处理与安全

- Cron 缺少或使用错误密钥时返回 401，不创建任务、不调用 DeepSeek。
- 管理员手动同步必须通过现有 Supabase Auth 和管理员权限检查。
- 防重入锁确保同一时间只有一个同步任务。
- DeepSeek 超时、429、5xx 和无效 JSON 使用有限重试；任务结束后保留 `failed` 状态供下次重试。
- 单条内容失败不阻断其他内容；单个语言失败不影响另一个语言。
- 数据库保存使用事务或等价的原子更新，不能暴露半篇新译文。
- 用户可控输入进入查询、日志和页面前保持现有转义与 Markdown 清理策略。
- DeepSeek、Cron 和 Supabase Service Role 密钥仅存在于服务器环境。

- locale 白名单、默认语言和 URL 前缀转换。
- 三份固定字典 key 完整且类型一致。

- 代码块、链接、图片、HTML 与占位符保护。
- DeepSeek 返回 JSON 和 Markdown 完整性校验。
- 源哈希未变化时不会调用 DeepSeek。

### 13.2 集成测试

- 首次访问不读取浏览器语言并显示简体中文。
- 手动切换后 Cookie 和站内路由保持所选语言。
- 公开页面和后台页面在三种语言下均可访问。
- 英文、日文内容读取正确译文；待处理或失败时回退中文并显示提示。
- 中文修改多次后，每日任务只翻译最终版本中的变化块。
- 中文记录删除后译文级联删除。
- 中文、英文、日文搜索命中对应内容。
- Cron 密钥、管理员鉴权、防重入和失败重试有效。

### 13.3 构建与人工验收

## 15. 成功标准

- 新访客默认看到简体中文，不受浏览器语言影响。
- 访客可在任何博客或后台页面切换简体中文、英文和日文，并保持当前页面和语言偏好。
- 固定界面在三种语言下没有明显漏译 key。
- DeepSeek 每天北京时间 2 点只翻译新增或变化的文本块。
- 未变化、删除和受保护内容不消耗翻译 Token。
- AI 译文成功后自动公开；未完成或失败时安全回退中文。
- 评论原文、代码、链接、图片地址和 slug 不被翻译或破坏。
- Cron 和管理员入口无法被未授权用户用于消耗 DeepSeek 配额。
- 现有博客、后台、Supabase 数据和缓存行为没有功能回退。
