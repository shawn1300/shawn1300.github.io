# DeepSeek 翻译超时自适应拆批设计

日期：2026-08-02

## 背景与诊断证据

已上线的断点翻译能够处理重复或缺失 ID，但 DeepSeek 请求仍可能在 45 秒客户端期限内没有返回。当前实现会把发生 `AbortError` 的相同批次原样重试三次，单个译文任务可能因此消耗约 135 秒，并且在整个批次没有返回时无法保存任何译文。

线上只读诊断确认：

- 最近 12 轮同步耗时为 189～239 秒，接近 240 秒应用级期限。
- “Mon, 13 Jul 2026 综合实验”正文约 3,212 字，包含 114 个可翻译 Markdown 块，最大单块仅 264 字。日文记录没有保存任何正文块，因此问题不是单块过大，而是大量小块被合并成同一个慢请求。
- “OSPF网络类型”和“OSPF特性”的请求也出现相同中止错误，说明偶发模型延迟和两个并发请求也会触发问题。
- 每种语言的 37 个等待项由 1 篇尚未创建译文的日记、10 个分类和 26 个标签组成，不是新的失败记录。

本设计是现有《DeepSeek 翻译管线容错与提速设计》的超时补充，不改变 Vercel、Supabase 或 DeepSeek 的总体架构。

## 方案比较

### 方案 A：只延长单请求超时

把 45 秒提高到 60～90 秒，改动最小，但相同请求多次重试会更快耗尽 240 秒运行期限，失败前仍然没有断点。不采用。

### 方案 B：只降低固定字符批次

把 6,000 字符降到更小值可以改善长内容，但不能限制大量短 Markdown 块产生的 JSON 条目数量，也不能处理较小请求的偶发超时。仅作为基础限制，不单独采用。

### 方案 C：固定双重上限并在超时后自适应二分

每批同时限制字符数和条目数。多条目请求第一次超时后不再原样重试，而是立即二分为更小子批次；当前运行的后续任务降为单并发。该方案能更早保存成功断点，同时保留对瞬时网络错误和 HTTP 限流的有限重试。采用此方案。

## 批次规划

`translateInBatches` 同时采用两个默认上限：

- `TRANSLATION_BATCH_CHARACTERS=2000`
- `TRANSLATION_BATCH_ITEMS=16`

任一上限即将被超过时开始新批次。单个翻译项不在此层按字符截断，避免破坏 Markdown 语义；现有 Markdown 拆分器已确认本次失败内容的最大文本块远低于字符上限。

环境变量允许以后调整上限。字符数最小限制为 500，条目数限制在 1～50，非法值回退到默认值。标题、摘要和正文块仍使用原有稳定 ID。

## 超时处理

DeepSeek 适配器新增可识别的超时错误，不再把 `AbortError` 当作普通网络错误原样重试三次：

1. 多条目请求第一次超过 45 秒后，立即拆成数量接近的两个子批次。
2. 两个子批次依次请求，避免同一译文内部继续放大并发。
3. 子批次成功结果合并回原结果；若后续子批次失败，已成功结果通过现有 `DeepSeekPartialError` 返回并立即保存。
4. 单条目请求允许再重试一次；第二次仍超时则记录明确错误：`DeepSeek request timed out after 45 seconds`。
5. `TypeError` 等瞬时网络故障，以及 HTTP 408、409、429 和 5xx，继续使用现有有限退避策略。
6. 接近本轮总期限时仍由现有 deadline 检查停止，不启动无法安全完成的新请求。

## 并发降级

DeepSeek 选项增加 `onTimeout` 回调。任意请求发生超时后：

- 当前已启动的并发波次自然结束，不强行取消另一个请求。
- 同一轮后续波次改为单并发。
- 下一轮手动同步重新从配置的并发 2 开始；若仍超时会再次自动降级。
- Cron 继续固定为单并发。

后台同步结果沿用 `rateLimited`，并新增 `timedOut`，用于记录本轮发生过超时。界面可以复用现有提示区域显示“检测到慢请求，已自动降为单并发”，但不要求用户介入。

## 断点与队列行为

数据库结构不变，也不需要执行新的 SQL。

每个固定小批次完成后，仍通过现有回调立即写入 `translated_blocks`。自适应二分发生部分成功时，也必须在错误写入前保存成功子批次。下一轮根据块哈希只请求缺失块。

失败译文继续排在缺失和等待项之后。用户不应在每轮开始前反复点击“重试全部”，因为重置为 `pending` 会让旧失败日记重新进入普通等待队列；完成其他 37 个等待项后，再对失败内容执行重试即可。

## 测试与验收

单元测试至少覆盖：

- 固定批次同时遵守 2,000 字符和 16 条目上限。
- 多条目请求抛出 `AbortError` 后不原样重试，而是二分并合并成功结果。
- 一个子批次最终失败时，另一个子批次的成功结果仍通过部分错误返回。
- 单条目超时只额外重试一次，并返回明确超时信息。
- 超时回调只需触发一次即可让同步器后续波次降为单并发。
- 现有重复 ID、Markdown 保护、429 降级和断点复用测试继续通过。

部署验收：

1. 不执行数据库迁移，也不要求新增 Vercel 环境变量；代码默认值直接生效。
2. 对“综合实验”日文点击单项重试并启动同步。
3. 后台可观察到该日记的已保存块逐轮增加，而不是连续多分钟保持 0。
4. OSPF 两篇超时内容能够复用同一机制完成，或者只留下明确的单块超时错误。
5. 同步运行不再因一个慢批次反复占满约 240 秒，等待的分类和标签能够继续推进。
6. `npm test`、TypeScript、ESLint 和 Next.js 生产构建通过。
