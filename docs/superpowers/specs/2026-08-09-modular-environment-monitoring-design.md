# 模块化环境监测与交互图表设计

日期：2026-08-09  
状态：设计已确认，等待用户审阅书面规格后进入实施计划

## 1. 背景

当前环境监测已经形成稳定的生产链路：两只米家温湿度计通过 Home Assistant 每 10 分钟调用私有写入接口，服务端将室内、室外温度、湿度和电量保存到 Supabase，并通过独立的 `/environment` 页面及公开 `latest/history` 接口展示最近 24 小时和 7 天数据。

现有实现把场所固定为 `home`，设备角色固定为 `indoor/outdoor`，读数结构固定为温度、湿度和电量。图表能够显示趋势，但不能通过鼠标、触摸或键盘检查具体数据点。本设计在不破坏现有 Home Assistant 链路和旧公开接口的前提下，实现以下目标：

1. 为趋势图增加 PC 鼠标、手机触摸和键盘数据点提示。
2. 支持通过配置和数据库迁移新增场所、设备及指标，不建设后台管理页面。
3. 第一阶段环境指标支持温度、湿度、CO₂ 和 PM2.5；电量作为设备健康指标继续保留。
4. Home Assistant 与 DIY ESP32 均通过统一的私有写入 API 上传，每个数据源使用独立令牌，默认周期为 10 分钟。
5. PM2.5 同时提供中国和美国 AQI 参考结果；CO₂ 提供明确标注的室内通风参考。
6. 在项目中提供从配置、迁移、令牌到设备上传和故障排查的完整教程。

## 2. 不在本阶段范围内

- 不建设场所、设备或令牌的博客后台管理页面。
- 不允许 ESP32 持有 Supabase Service Role Key 或直接写 Supabase 原始表。
- 不开放 Home Assistant 公网管理端口。
- 不实现告警推送、自动设备控制或家电联动。
- 不把消费级传感器计算结果描述为官方监测、医疗结论或安全证明。
- 不删除现有环境表；是否归档旧表留待新版稳定运行后的独立阶段。
- 不在本阶段实现 VRChat 桥接，但继续保护旧公开接口契约供其使用。

## 3. 总体架构

采用规范化的“场所 → 数据源/设备 → 指标 → 读数”模型：

```text
Home Assistant ─┐
                ├─ Bearer Token ─→ POST /api/environment/v2/ingest
ESP32 A ────────┤                         │
ESP32 B ────────┘                         ▼
                                   模块化环境表
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
     v2 模块化公开 API 与页面                         v1 indoor/outdoor 兼容投影
                 │                                               │
     /environment/<location>                          旧 latest/history 与未来 VRChat
```

运行时数据库是场所和设备元数据的权威来源。项目内的声明式配置是新增或修改元数据的审阅入口；配置工具负责验证并生成 Supabase SQL 迁移，但不会自动修改生产数据库。

## 4. 数据模型

### 4.1 场所

继续使用 `environment_locations`，扩展以下配置能力：

- 稳定的 `slug` 与中、英、日名称。
- IANA 时区。
- 是否公开；新增场所默认公开。
- 展示顺序与启用状态。
- 可选的主要室内/室外设备比较配置。

只有启用且公开的场所出现在公开场所列表和页面选择器中。所有环境页面继续设置 `noindex, nofollow`，且不进入 sitemap。

`home` 配置主要室内设备和主要室外设备，并保留温度、湿度“室内减室外”差值。其他场所默认不配置比较关系，因此不显示差值模块。

### 4.2 数据源

新增 `environment_sources`：

- `id`、稳定 `slug`、显示名称与启用状态。
- 来源类型：`home_assistant` 或 `esp32`。
- 高强度随机令牌的 SHA-256 摘要与轮换时间；不保存明文令牌。
- 创建和更新时间。

一个数据源可以拥有多台设备；一台设备只归属于一个数据源。每个 Home Assistant 实例和每块 ESP32 使用独立令牌，以便单独撤销和轮换。

### 4.3 设备

新增 `environment_devices`：

- 所属场所和数据源。
- 场所内唯一的设备 `slug`。
- 中、英、日名称。
- `indoor`、`outdoor` 或 `other` 放置角色。
- 展示顺序和启用状态。

内部数据库 UUID、数据源 slug 和令牌摘要不得进入公开响应。

### 4.4 指标

新增 `environment_device_metrics`。第一阶段注册表包含：

| 指标键 | 单位 | 硬范围 | 默认图表 |
|---|---:|---:|---|
| `temperatureC` | `°C` | `-30..100` | 是 |
| `humidityPercent` | `%` | `0..100` | 是 |
| `co2Ppm` | `ppm` | `1..50000` | 是 |
| `pm25UgM3` | `µg/m³` | `0..5000` | 是 |
| `batteryPercent` | `%` | `0..100` | 否，仅设备状态 |

指标注册表在代码中定义单位、格式、硬范围、聚合方式、图表能力和多语言消息键。数据库只允许注册表中的指标键。单台设备可以声明任意受支持的指标组合。

### 4.5 读数

新增 `environment_metric_readings`，每行只保存一台设备的一项指标：

- `metric_id`
- 数值
- `source_updated_at`
- `collected_at`
- 服务端 UTC 十分钟桶
- 幂等键

`(metric_id, ten_minute_bucket)` 唯一。同一指标在同一服务端十分钟桶内重复上传不新增记录。读数保留策略继续按 `collected_at` 删除 30 天以前的数据，且只影响环境读数表。

所有新表启用 RLS，不提供匿名或普通 authenticated 客户端的原始表策略。服务端 Route Handler 使用现有 Service Role 客户端进行写入和安全投影。

## 5. 现有数据与接口兼容

### 5.1 数据迁移

一次性迁移执行以下操作：

1. 复用现有 `home` 场所。
2. 创建 Home Assistant 数据源。
3. 将现有室内、室外传感器映射为两台新设备。
4. 为两台设备创建温度、湿度和电量指标。
5. 将现有最近 30 天读数拆为规范化指标读数，保留原 `source_updated_at` 和 `collected_at`。
6. 为 `home` 配置主要室内、室外设备比较关系。

迁移必须原子执行，并对迁移前后每个角色的记录数、最新时间和值进行核对。现有三张表暂时保留，不在本阶段删除。

### 5.2 v1 写入兼容

当前 `POST /api/environment/ingest` 的认证、请求格式和固定响应保持兼容。验证后的 `indoor/outdoor` 负载由适配层转换成 v2 设备指标写入，不再向旧读数表双写。

当前 `ENVIRONMENT_INGEST_TOKEN` 在过渡期继续只认证 v1 Home Assistant 路径。迁移完成后可以按照教程将 Home Assistant 切换到独立的 v2 数据源令牌，但切换不阻塞新版上线。

### 5.3 v1 公开兼容

现有：

- `GET /api/environment/latest?location=home`
- `GET /api/environment/history?location=home&range=24h|7d`

继续返回原有 `indoor/outdoor` 类型和字段。兼容服务从 v2 规范化表读取 `home` 的主要室内、室外设备，并投影回旧响应。现有新鲜度、差值、24 小时原始数据、7 天小时聚合和缓存上限保持不变。

## 6. v2 私有写入 API

新增 `POST /api/environment/v2/ingest`，使用 Node.js runtime、HTTPS 和 `Authorization: Bearer <token>`。

请求示例：

```json
{
  "schemaVersion": 2,
  "sentAt": "2026-08-09T10:00:00Z",
  "readings": [
    {
      "device": "living-room-air",
      "sourceUpdatedAt": "2026-08-09T09:59:40Z",
      "metrics": {
        "temperatureC": 26.4,
        "humidityPercent": 58,
        "co2Ppm": 720,
        "pm25UgM3": 8.6
      }
    }
  ]
}
```

处理顺序：

1. 限制正文大小并取得 Bearer Token。
2. 对令牌求摘要并识别已启用数据源；认证失败时不解析或记录正文。
3. 校验版本、UTC 时间、设备不重复和指标结构。
4. 验证设备属于该数据源、设备已启用且指标已声明。
5. 在服务端和数据库两层执行指标范围约束。
6. 为每个有效指标生成十分钟幂等写入。
7. 返回按设备和指标排序的固定 `stored`、`duplicate` 或 `skipped` 结果。

温度、湿度或其他单项无效时只跳过该指标；同一设备及同批其他设备的有效指标继续保存。全部指标无效返回 `422`。数据库不可用返回通用 `503`。设备等待下一个十分钟周期，不执行高频重试。

请求和日志不得包含明文令牌、数据库错误、内部 UUID、Home Assistant 实体 ID、小米标识或设备 Wi-Fi 信息。

## 7. v2 公开读取 API

新增：

- `GET /api/environment/v2/locations`
- `GET /api/environment/v2/locations/<slug>/latest`
- `GET /api/environment/v2/locations/<slug>/history?range=24h|7d`

只返回启用且公开的场所、设备显示信息、获准指标、规范化数值、单位、源更新时间、新鲜度和派生参考结果。

`latest` 按设备和指标返回最新值；以 25 分钟为默认新鲜度界限。`history` 的 24 小时范围返回按时间排序的原始十分钟读数，7 天范围按场所时区聚合为小时平均。每台设备和每个指标设置查询上限，并始终降序取得最新一批后恢复升序，采集频率变化时优先保留最新数据。

公开响应不得包含数据源、令牌摘要、内部 ID、幂等键、`collected_at` 或数据库错误。

## 8. 页面路由与场所切换

页面路由：

- `/environment` 默认展示 `home`。
- `/environment/home` 与默认页内容一致。
- `/environment/<location-slug>` 展示独立场所。
- 英文和日文继续使用现有 locale 前缀。

顶部增加场所选择器。选择器只列出公开且启用的场所，通过 Next.js 客户端导航跳转到独立路径，并预取可访问页面。切换时保留页面骨架、主题、语言控件和上一张有效快照，显示低干扰加载状态；成功后替换内容，失败时保留旧页面并提供明确错误，不出现整页白屏。

页面按场所元数据自动生成：

- 当前设备卡片，显示设备名称、放置角色、支持的最新指标和电量。
- 只为实际存在的温度、湿度、CO₂、PM2.5 指标生成趋势模块。
- 每个趋势模块继续提供 24 小时和 7 天切换。
- `home` 显示主要室内减主要室外的温湿度差值；其他场所不显示差值。
- 数据缺失、延迟、部分设备和请求失败均保留真实状态，不补假数据。

所有场所页面继续与博客 Header、Footer、音乐播放器和返回顶部组件隔离，设置 `noindex, nofollow`，且不加入博客导航或 sitemap。

## 9. 图表数据点交互

### 9.1 命中规则

图表模型保留每个真实点的屏幕坐标、设备标识、指标值和时间。指针移动时，在当前指标的全部可见曲线中计算二维屏幕距离，只选择最近的一条曲线和一个数据点。不得同时显示室内、室外或其他设备的组合提示。

当最近点超过合理命中半径时隐藏提示，避免指针在远离曲线处仍显示无关值。命中算法是与 React 组件分离的纯函数，以便用固定几何输入测试。

### 9.2 PC 与手机

- PC：鼠标进入图表绘图区后更新最近点，离开后隐藏。
- 手机：使用 Pointer Events；手指按住并水平移动时更新最近点，松开或取消后隐藏。
- 图表允许页面纵向滚动，只有明确的横向检查手势用于数据点交互。
- 交互期间显示垂直参考线、选中点和浮动提示框。
- 提示框显示场所、设备名称、场所时区格式化时间、指标值和单位。
- 提示框根据选中点和视口边缘自动换边，不被容器或屏幕裁切。

### 9.3 键盘与可访问性

图表可聚焦。左右方向键沿当前曲线切换时间点，上下方向键切换到相邻设备曲线，Escape 清除选择。屏幕阅读器通过状态区域获得与提示框等价的设备、时间和值。曲线同时使用颜色、实线/虚线和点型区分，状态不只依赖颜色。

## 10. PM2.5 与 AQI 参考

PM2.5 卡片同时显示：

- 最新传感器浓度，单位 `µg/m³`。
- 中国 AQI 参考值、等级、计算时间、标准版本和样本状态。
- 美国 AQI 参考值、等级、计算时间、标准版本和样本状态。
- “消费级传感器计算参考，不是官方监测站数据”的固定说明。

十分钟读数先按场所时区形成小时浓度。中国计算器严格实现 2026 年 3 月 1 日生效的 `HJ 633—2026` 颗粒物实时报计算方法、数据完整性和断点；美国计算器严格实现 EPA 2026 NowCast、当前 PM2.5 断点、浓度截断和修约规则。两个计算器分别版本化，不能共享一个被误认为相同标准的结果。

任一标准的数据完整性条件不满足时，该标准结果返回 `insufficient_data`，页面显示“样本不足”，不得用最新瞬时值替代 AQI。AQI 模块仅对配置了 PM2.5 指标且启用 AQI 展示的设备出现。

权威来源：

- 中国生态环境部《环境空气质量指数（AQI）技术规定》HJ 633—2026：<https://www.mee.gov.cn/ywgz/fgbz/bz/bzwb/jcffbz/202602/t20260225_1144441.shtml>
- 美国 EPA 当前 AQI 断点：<https://aqs.epa.gov/aqsweb/documents/codetables/aqi_breakpoints.html>
- 美国 AirNow 2026 AQI 技术文档：<https://www.airnow.gov/publications/air-quality-index/technical-assistance-document-for-reporting-the-daily-aqi/>

## 11. CO₂ 通风参考

CO₂ 卡片显示最新浓度、最近一小时平均值和通风参考。最近一小时至少需要 4 个有效十分钟样本；不足时只显示当前浓度和“样本不足”。

通风参考按一小时平均值分为：

- `< 800 ppm`：通风良好。
- `800..1500 ppm`：通风尚可，建议关注。
- `> 1500 ppm`：通风较差，建议改善。

页面固定说明 CO₂ 只是通风状况的宽泛参考，不代表安全浓度，也不能代表完整室内空气质量。该分级参考英国 HSE 的 CO₂ 通风监测指导：<https://www.hse.gov.uk/ventilation/using-co2-monitors.htm>。

## 12. 配置与迁移工作流

新增一个不含密钥的声明式环境配置，描述：

- 场所 slug、多语言名称、时区、公开状态和顺序。
- 数据源 slug、类型和显示名称，不含令牌。
- 设备 slug、多语言名称、数据源、场所、放置角色和顺序。
- 设备启用的指标及可选 AQI 展示。
- 场所主要室内/室外比较设备。

配置工具提供：

1. `validate`：只读检查 slug 格式和唯一性、引用完整性、设备归属、指标合法性、主要设备比较关系和多语言字段。
2. `generate-migration`：根据已验证配置生成可审阅、可重复执行的 Supabase SQL 迁移文件。
3. `generate-token`：在本机生成至少 32 字节的随机令牌，将明文复制到剪贴板，只输出令牌摘要和更新数据库所需的非明文材料；明文不得写入项目或终端日志。

生成迁移不会自动连接或修改生产数据库。用户必须审阅 SQL，并通过既有 Supabase 运维流程执行。

## 14. 错误处理

- 写入认证失败：固定 `401 UNAUTHORIZED`，认证前不解析正文。
- 媒体类型错误：`415 UNSUPPORTED_MEDIA_TYPE`。
- 正文过大：`413 PAYLOAD_TOO_LARGE`。
- JSON 或结构错误：固定 `400/422` 代码。
- 数据源不能写目标设备：固定 `422 DEVICE_NOT_ALLOWED`，不说明目标是否属于其他来源。
- 单项无效：该项 `skipped`，其他有效项继续。
- 全部无效：`422 NO_VALID_METRICS`。
- 数据库或服务暂时不可用：固定 `503 SERVICE_UNAVAILABLE`。
- 未知、停用或非公开场所：公开 API 固定 `404 LOCATION_NOT_FOUND`。
- 页面场所切换失败：保留上一场所快照，并提供可重试提示。
- AQI 或 CO₂ 样本不足：返回结构化 `insufficient_data`，不是服务错误。

日志只记录固定代码、数据源内部审计引用、有效/跳过指标数量和耗时，不记录正文、令牌或测量值。

## 16. 上线与回滚

按以下顺序上线：

1. 部署新表、配置验证器和现有数据迁移，核对迁移结果。
2. 部署 v2 写入/读取服务和 v1 兼容适配，保持现有 Home Assistant 请求不变。
3. 部署模块化场所页面和交互图表。
4. 发布配置教程和 ESP32 示例，使用独立测试数据源完成真实验收。
5. 稳定运行后，再单独评估旧表归档；本阶段不删除旧表。

数据库迁移前创建备份。若 v2 发布失败，先回滚应用版本并停止新 v2 数据源；现有旧表仍保留。回滚期间产生在 v2 表中的读数不删除，修复后重新启用并核对。任何回滚不得恢复已废弃的 Xiaomi 密码、Cookie、MiService 或浏览器捕获路线。

## 17. 完成定义

满足以下条件才视为本阶段完成：

- 用户能按项目教程新增场所、Home Assistant/ESP32 数据源、设备和支持指标，无需修改页面组件。
- 当前 Home Assistant 继续每十分钟写入，旧公开接口响应兼容。
- `/environment` 默认 `home`，场所选择器可无明显闪烁地进入独立页面。
- PC、手机和键盘都能检查最近单条曲线的数据点。
- PM2.5 中国/美国参考值与 CO₂ 通风参考有版本、样本状态和非官方说明。
- 新旧数据均遵守 RLS、安全投影、十分钟幂等和 30 天保留。
- 自动测试、静态检查、生产构建和真实设备验收全部通过。
