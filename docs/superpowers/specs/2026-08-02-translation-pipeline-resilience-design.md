# DeepSeek 翻译管线容错与提速设计

日期：2026-08-02

## 背景

首次全量翻译时，Vercel 函数在约 4 分钟的应用级安全期限内只能完成约 8～10 条内容。当前同步每次从英文队列开头逐项读取译文状态，导致已完成项产生重复数据库查询，日文长期得不到处理。一篇长日记还触发了 `DeepSeek returned an unexpected or duplicate id`：模型在批量响应中重复返回块 ID，程序因此丢弃整批结果并把整篇内容标记为失败。

现有部署继续使用 Vercel、Supabase 和 DeepSeek，不增加队列或其他后端服务。

## 目标

- DeepSeek 返回重复、缺失或异常 ID 时，只重试受影响的块，不丢弃其他成功译文。
- 每个成功批次立即保存断点；函数超时、页面关闭或网络中断后能够续传。
- 一次读取源内容和译文状态，直接跳过当前且完整的译文。
- 英文和日文公平交替处理。
- 后台手动同步采用两个并发请求，并在 `partial` 后自动启动下一轮。
- Cron 保持单并发，适合每天少量增量。
- 后台能直接定位失败内容、查看错误并重试。
- 等待、完成和失败数量包括尚未创建译文行的历史内容。

## 非目标

- 不引入 Vercel Workflow、消息队列或第三方任务服务。
- 不保证关闭后台页面后仍自动连续执行多轮；已启动的当前轮次和已保存断点不受影响。
- 不提高 Vercel 平台的函数硬性时限。
- 不并行写入同一条内容的同一语言译文记录。

## 总体架构

### 1. 批量任务规划

同步开始时并行读取已发布文章、日记、分类、标签和四张译文表。规划器在内存中按源哈希、状态和语言生成任务，不再由每个任务单独查询现有译文。

队列优先级为：

1. 缺失译文
2. `pending`、`processing` 或源哈希过期的译文
3. `failed` 译文

当前且状态为 `complete` 的译文直接计为复用。失败项排在未完成内容之后，避免同一失败内容在每轮开头反复消耗时间。

### 2. 公平队列与受控并发

任务按源内容交替语言，例如“文章 A 英文、文章 A 日文、文章 B 英文、文章 B 日文”。手动同步将不同译文记录组成最多两个任务的并发波次；Cron 始终使用单任务波次。

环境变量 `TRANSLATION_CONCURRENCY` 控制手动并发，默认 `2`，代码限制在 `1～4`。收到 DeepSeek HTTP 429 后，当前运行自动降为单并发并按退避策略重试。并发只改变速度，不改变翻译内容或发布规则。

### 3. 更小批次与运行期限

单个内容继续按 Markdown 块翻译，但默认批次字符数从 12,000 降到约 6,000，并允许通过 `TRANSLATION_BATCH_CHARACTERS` 调整。标题、摘要和正文块使用稳定 ID。

运行期限不仅在内容之间检查，也在每个 DeepSeek 批次前检查。接近期限时停止启动新请求，保存现有断点并返回 `partial`，给 Vercel 留出完成数据库写入和响应的安全余量。

## DeepSeek 响应容错

响应解析器不再遇到一个错误就抛弃整批：

- 正常且唯一的预期 ID 被接受。
- 重复 ID 被标记为未解决；该 ID 的所有候选结果暂不采用。
- 缺失 ID 被标记为未解决。
- 未知 ID 被忽略并写入诊断信息。
- 格式错误的条目只影响自身。

正常结果先进入翻译映射。未解决项使用更小子批次重试；仍然异常时拆成单项请求。网络错误、408、409、429 和 5xx 最多进行有限次数退避重试。单项最终失败后，保存具体错误并继续其他任务。

受保护的 Markdown 占位符仍必须逐一恢复和验证。占位符异常只重试对应块。

## 断点保存

现有译文表已经包含 `source_blocks`、`translated_blocks`、标题/摘要哈希和状态字段，无需新增数据库表。

开始处理时写入当前源哈希并将状态设为 `processing`。每完成一个 DeepSeek 子批次，就合并并写回：

- 已完成标题或摘要
- `translated_blocks`
- 当前源块和对应哈希
- 清空本批次已解决的临时错误

只有标题和全部可翻译块齐全后才重建完整 Markdown，并原子更新为 `complete`。公开读取策略仍只允许 `complete`，因此处理中断点不会被访客看到。下一轮从已保存块继续，只翻译缺失部分。

## 自动连续运行

后台“立即执行同步”改为连续模式：

1. 发起一轮手动同步。
2. 收到 `partial` 且仍有可处理项时，等待数秒后自动发起下一轮。
3. 页面实时刷新完成、等待、失败、当前轮次和语言进度。
4. 全部完成、用户停止、登录失效、配置错误或只剩无法继续的失败项时停止。

关闭页面只阻止后续轮次。服务端当前请求如果仍在执行，会按正常期限结束；已经保存的断点不会丢失。重新打开页面可继续。

同步结果增加 `remainingCount`、`madeProgress` 和 `canContinue`。连续模式在一轮没有进展时必须停止，防止无限循环。Cron 只执行一轮，不进行服务端自调用。

## 失败详情与重试

状态接口返回译文的 `last_error`、`retry_count`、更新时间、内容类型、源 ID 和中文标题。后台新增失败列表，提供：

- 错误内容与目标语言
- 重试次数和完整错误
- “重试此项”
- “重试全部失败项”

重试操作只把指定译文状态重置为 `pending` 并清空本次错误，不删除已经保存的成功块。连续模式遇到仅剩失败项时停止，由用户查看错误后决定重试；下一次 Cron 仍可按正常策略尝试瞬时错误。

## 统计口径

状态接口以所有中文源内容乘以两个目标语言作为期望集合，再与译文表合并：

- `complete`：当前完整译文
- `failed`：最后一次处理失败
- `processing`：已有断点但未完成
- `pending`：数据库标记待处理、源已变化或译文行尚不存在

因此首次部署时不会再显示“等待 0”。运行记录继续记录扫描、复用、翻译块和失败数量，并在后台展示 `error_summary`。

## 安全与成本

- API Key 和 Service Role Key 继续只存在于服务端环境变量。
- 运行锁继续保证同一时间只有一个同步运行；浏览器重复点击不会创建并行运行。
- 两个并发只处理不同译文记录。
- 成功块即时保存和哈希复用可避免重复 Token。
- 429 自动降级到单并发，防止持续限流放大重试成本。

## 测试与验收

单元测试覆盖：

- 重复 ID 时保留其他唯一结果，仅重试异常 ID。
- 缺失、未知、格式错误和占位符错误的分离处理。
- 大批次递减为小批次和单项重试。
- 每批保存断点并从断点恢复。
- 规划器跳过当前完整译文，并按英日交替排序。
- 手动并发为 2、Cron 并发为 1，429 后降级。
- 仅剩失败项或无进展时连续模式停止。
- 缺失译文行正确计入等待数量。

集成验收：

- 当前失败日记能够自动完成英文译文，不需修改中文正文。
- 首次同步时英文和日文完成数同时增长。
- 连续模式可由一次点击运行多轮并最终停止。
- 页面中断后重新运行不会重新消耗已完成块的 Token。
- `npm test`、TypeScript、ESLint 和 Next.js 生产构建通过。
