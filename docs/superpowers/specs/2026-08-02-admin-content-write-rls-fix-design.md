# 后台文章与日记保存 RLS 冲突修复设计

日期：2026-08-02

## 问题诊断

多语言迁移为 `posts` 和 `diaries` 增加了源内容变更触发器。文章或日记保存后，触发器会把对应英文、日文译文写成 `pending`，等待下一轮增量翻译。

译文表启用了 RLS，且有意只提供完整译文的读取策略，没有登录用户写入策略。现有保存接口使用名为 `createServiceClient` 的 SSR 客户端，并同时读取登录 Cookie。Supabase 客户端在存在用户会话时优先使用用户 access token，而不是构造客户端时传入的 Service Role Key。因此源表更新本身通过认证用户策略后，触发器写译文表会被 RLS 拒绝，整个事务回滚；前端最终只显示“保存失败，请重试”。

## 目标

- 登录后台后可以新建、修改和删除文章与日记。
- 修改中文标题、摘要或正文后，数据库触发器正常把英文、日文译文标记为 `pending`。
- 登录验证仍使用真实用户会话，未登录请求不能借用 Service Role。
- Service Role Key 只在服务端使用，不进入浏览器代码或接口响应。
- 保存失败时优先显示接口返回的安全错误信息。
- 不执行新的数据库迁移，不修改现有译文和翻译断点。

## 方案比较

### 方案 A：验证客户端与写入客户端分离

先用携带 Cookie 的普通服务端客户端调用 `auth.getUser()`；确认用户存在后，再创建无 Cookie 的 `createAdminSupabase()` 执行数据库写入。触发器随 Service Role 写入事务运行，可以更新译文状态。无需 SQL，权限边界清晰。采用此方案。

### 方案 B：把四个翻译触发器改为 `SECURITY DEFINER`

源表继续使用认证用户令牌写入，触发器以函数所有者权限更新译文表。改动集中在数据库，但需要用户再次执行 SQL，并且必须严格设置 `search_path` 和函数所有权。当前问题可以在应用层安全解决，因此不采用。

### 方案 C：给认证用户增加译文表写入策略

实现最简单，但会允许浏览器客户端直接篡改译文正文、状态和错误信息，破坏“只有服务端翻译器能写译文”的现有安全设计。不采用。

## 服务端结构

在服务端 Supabase 模块附近增加一个小型认证辅助函数：

1. 使用 `createServerSupabase()` 读取并验证用户。
2. 用户不存在时返回未认证结果。
3. 用户存在时返回用户对象和 `createAdminSupabase()` 创建的无 Cookie 客户端。

该辅助函数必须导入 `server-only`，并且只允许 Route Handler 使用。它不判断新的管理员角色，因为项目现有策略就是“唯一认证用户可以管理内容”；本次修复保持该权限模型不变。

## 路由调整

以下写操作改用认证辅助函数：

- `POST /api/posts`
- `PUT /api/posts/[id]`
- `DELETE /api/posts/[id]`
- `POST /api/diaries`
- `PUT /api/diaries/[id]`
- `DELETE /api/diaries/[id]`

每个请求先完成用户验证，再使用返回的无 Cookie 客户端写源表和文章标签关系。读取接口暂不改变，因为它们不触发译文写入。

文章更新仍按现有顺序保存文章、删除旧标签关系、写入新标签关系；本次不扩张为数据库事务重构。日记保持单表写入。成功后继续刷新现有 `posts` 或 `diaries` 缓存标签。

分类和标签管理页面目前从浏览器直接写 Supabase，虽然相同翻译触发器也可能造成权限冲突，但它不属于用户本次报告的文章/日记保存路径。本次不新增分类标签 API；后续实际出现保存问题时再单独迁移，避免扩大改动范围。

## 错误处理

- 未登录请求继续返回 HTTP 401 和“请先登录”。
- slug 唯一冲突继续返回 HTTP 409 和现有明确提示。
- 其他数据库错误只写入 Vercel 服务端日志，接口返回现有安全的中文错误，不直接暴露表结构或 Service Role 信息。
- 文章和日记编辑器在接口返回 `error` 字段时显示该字段；字段不存在、响应不是 JSON 或网络失败时，回退到本地化的“保存失败，请重试”。

## 安全边界

- 浏览器请求永远拿不到 Service Role Key。
- 只有服务端成功验证 Supabase 用户后才创建管理写客户端。
- 不给译文表新增 INSERT、UPDATE 或 DELETE 的客户端 RLS 策略。
- 不修改自动翻译、Cron 和后台翻译接口现有的鉴权方式。
- 不修改或提交工作区中未跟踪的二维码图片。

## 测试与验收

代码验证：

- TypeScript 检查通过，确保各路由正确处理认证结果和用户 ID。
- ESLint 无新增错误。
- Next.js 生产构建通过。
- 现有自动翻译单元测试继续通过。

部署验收：

1. 登录后台修改一篇已完成翻译的文章并保存成功。
2. 登录后台修改一篇已完成翻译的日记并保存成功。
3. 只读检查源内容已经更新，对应英文、日文译文状态变为 `pending`。
4. 后台自动翻译页面的等待数量增加；运行同步后只重译变化内容并重新变为 `complete`。
5. 未登录请求仍返回 401，且浏览器资源中不存在 Service Role Key。
